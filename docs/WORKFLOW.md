# WORKFLOW.md — 場所を移りながら進める運用

## 前提

- 状態の中心は GitHub。セッションやチャットの中の情報は引き継がれない前提で書く
- 入口は複数あってよい: スマホ（各社のクラウド / リモート環境）、自宅マシン（各 CLI を本人が起動）、Muse の VM

## 場所を移るときの作法

1. 作業を区切るときは必ず push する（未 push のローカル作業は他の場所からは存在しない）
2. 決定と仕様変更は Issue / PR に書く。チャットで決めたことも、確定したら Issue に転記する
3. 次の担当への受け渡しは `templates/HANDOFF.md` の形で PR か Issue に残す

## フェーズごとの置き場

仕様策定は Muse 固定。それ以外は人間がタスクごとに決めて Issue に書く。前段の作業者は、受け渡し時に次フェーズの推奨担当（エージェント／モデル、理由つき）を書いてよい。

| フェーズ | 置き場 | 担当 |
|---|---|---|
| 仕様策定 | Issue（SPEC 雛形） | Muse（固定） |
| 仕様ブラッシュアップ | Issue コメント | Muse 以外のエージェント |
| 実装 | ブランチ + PR | Issue で指定されたエージェント |
| クロスレビュー | PR レビュー | 実装者と別のエージェント |
| 検収・マージ | PR | 実装者以外が検収、人間がマージ判断 |

## 担当を決めるときの参考（決定ではない）

- Codex: ロジックが重い・精度が要る実装
- Claude Code: UI 寄りの実装、長文脈の調査、別モデルでのレビュー
- Muse: 仕様策定（固定）のほか、検収、スペース設置などの運用寄り

## レビュー待ちの間に

- レビューは非同期が前提。待ち時間は別の Issue の仕様策定や実装に使う
- PR は小さく分割し、1 PR = 1 つの論点にする
